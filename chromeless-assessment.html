Bottom line

Chromeless is in strong shape. Zero dependencies, clean module boundaries, security handled with real thought (origin-verified bridges, Keychain storage, CSP on internal pages, sanitized downloads), and a build script that is fully current. It has quietly grown from the single-file app the README describes into a ~30-feature browser: tabs, split view, history with FTS search, downloads, multi-account containers, autofill with Touch ID, customizable shortcuts, content blocking.

The pressing work is not features. This pass found three verified bugs (an unscoped Keychain query that exposes other apps' passwords in Settings, background tabs loading with no navigation delegate, and a close path that defeats ⌘⇧T restore), a README that describes a different product, ~150 lines of dead HUD code, a 3,200-line window controller that keeps accreting, and zero tests or CI. All of it is fixable in small, independent steps.

P0: verified bugs correctness and trust, fix first

P01. The password vault is not scoped to this app

Vault.query builds Keychain queries with only kSecClass + kSecAttrServer. There is no kSecAttrService. Consequences, all verified by reading the code:

  • Vault.allEntries() enumerates every internet-password item in the user's login keychain. Settings ▸ Passwords can display credentials saved by other applications.
  • Vault.delete and the update path of Vault.save can delete or overwrite another app's keychain item if server + account happen to collide.

Security/Vault.swift:18-25 (query), 29-42 (save), 73-75 (delete), 79-93 (allEntries)

FixAdd a constant kSecAttrService (e.g. "com.chromeless.app") to every query. One caveat: items already saved without the attribute become invisible afterward, so either migrate them on first launch (copy-and-delete) or accept that users re-save once.

P02. Background tabs load with no navigation delegate

newTab(url:background:) starts the load immediately for ⌘-clicked background tabs, but navigationDelegate/uiDelegate are only assigned for the first tab at window setup and later inside switchToTab. The web-view factory assigns neither. A background tab therefore loads with no delegate until it is first selected:

  • the visit is never recorded in history (didFinish never fires for it);
  • per-site zoom is not applied;
  • load errors are not surfaced;
  • a response that should become a download (decidePolicyFor navigationResponse) is not intercepted.

Browser/BrowserWindow.swift:443-461 (background load), 692-693 (delegates in switchToTab), 181-182 (first tab only); Browser/WebViewFactory.swift assigns none

FixAssign both delegates in newTab right after dequeueWebView (or in the factory), not only in switchToTab.

P03. Closing the last tab skips the recently-closed stack

closeCurrentTab (⌘W) pushes the URL onto ClosedTabStore before closing. The tab-strip close button path does not: when one tab remains, tabItemCloseClicked closes the window with no push, so ⌘⇧T cannot recover it.

Browser/BrowserWindow.swift:1065-1076 vs closeCurrentTab at 462-464

FixOne line: ClosedTabStore.push(tab.url) before window?.close().

P1: structural debt

P1Dead code: the entire HUD subsystem (~150 lines)

showHUD() has zero callers; ⌘L now routes through AppDelegate.openLocation to the inline omnibox. That leaves unreachable: the HUD build block, its layout branch, commitHUD, updateSuggestions, suggestionRowClicked, every isHUD: branch in the suggestion machinery, and the mouse-monitor HUD dismiss. Related dead items: BrowserWindowController.openLocation (shadowed by the AppDelegate version), BookmarkStore.findFolder, four unused ChromeFont suggestion fonts, the permanently-hidden tabBarSeparator, constant-zero tabToolbarOverlap, and pullEnabled (never set false; no setting exposes it).

FixDelete it. Removing the HUD also deletes half of the duplicated suggestion-keyboard handling for free.

P1The write-only visits table

Every page load inserts into visits (Data/History.swift:39-45). Nothing ever reads it. Either build something on it (visit counts, "frequently visited" on the start page) or drop the writes.

P1BrowserWindowController is a 3,200-line god object

~60 stored UI properties and 7 protocol conformances (window delegate, both WK delegates, text field delegate, menu validation, gesture delegate). buildChrome is ~320 lines; layoutOverlays is ~170 lines of manual frame math; the tab-close choreography (dissolve split, remove from hierarchy, close, switch) is copy-pasted across six call sites; KVO setup is duplicated between observeWebView and switchToTab; find is triplicated (findNext/findPrev/runFind differ only in direction).

FixExtract into Browser/ files: FindBarController, SuggestionsController, DownloadsPanel, ZenModeController, SiteSettingsPopover, AutofillBanner. The controller keeps navigation policy and tab orchestration. Also collapse to one find(direction:), one KVO-setup helper, and one close(tab:) primitive.

P1Zero tests, zero CI

No test target, no Package.swift, no GitHub Actions, no lint config. The irony: the purest logic in the app is already static and stateless and trivially testable: smartURL, Bangs.resolve, Keybindings encode/decode/conflict detection, FTS query sanitization, DownloadManager.sanitizedFilename, IdentityStore.registrableDomain.

FixAdd a Package.swift with a test target for those units, plus a macOS-runner workflow that just runs ./build.sh. The build script is current (it compiles every directory in one whole-module swiftc -O invocation), so CI is a 20-line file.

P1Fragile patterns worth a pass

  • Per-tab 1-second repeating Timer for audio state plus private APIs _isPlayingAudio/_setPageMuted: via unsafeBitCast (Tabs.swift:39, 48-92). Works, degrades gracefully, but N timers for N tabs and a permanent App Store blocker.
  • IdentityStore.all() hits SQLite on every call and runs in hot paths (tab-bar refresh, and per-navigation via host bindings). Cache it per transaction.
  • All SQLite runs synchronously on the main thread. Fine at this scale, unbounded as history grows.
  • registrableDomain uses a 14-entry hand-maintained two-level TLD set (Data/Identity.swift:202-215), so host routing mis-buckets things like foo.com.cn.
  • sqlite3_step return values are almost never checked; a DB open failure only prints and continues.
  • Zen mode animates via a hand-rolled 60 fps timer re-running layoutOverlays() every frame.

Security: what holds up, what doesn't

Done well

  • Passwords in the login Keychain as kSecClassInternetPassword with WhenUnlockedThisDeviceOnly. No plaintext secrets anywhere.
  • All JS bridges verify message.frameInfo.securityOrigin, never JS-supplied URLs. Autofill additionally requires a secure context (HTTPS or loopback) before save or fill.
  • Navigation policy denies top-level data:/javascript: documents; non-web schemes hand off to the OS only from the main frame.
  • Download filenames are contained against path traversal. Internal pages ship a restrictive CSP.
  • Passkey entitlement probed at runtime via SecTaskCreateFromSelf; WebAuthn hidden without it, so sites fall back cleanly.
